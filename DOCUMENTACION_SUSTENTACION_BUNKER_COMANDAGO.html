2. INTRODUCCIÓN Y CONTEXTUALIZACIÓN

2.1. Planteamiento del Problema: La Realidad de Dibal y el Mercado Gastronómico

El sector gastronómico peruano enfrenta una severa traba tecnológica debido a la dependencia de sistemas POS tradicionales y rígidos. Tras una auditoría exhaustiva a locales que operan con el software Dibal (sistema ampliamente extendido en restaurantes locales), identificamos que su arquitectura monolítica y obsoleta genera fricciones críticas en los flujos diarios de trabajo:

  • Fricción e Inseguridad en Impresión Local: Dibal obliga a ejecutar navegadores en formato especial de desarrollador desactivando banderas de seguridad, dependiendo ciegamente de paquetes como Laragon o XAMPP y colapsando cuando el router DHCP cambia la IP asignada a la impresora térmica.
  • Procesos Largos y Burocráticos en Caja: Para registrar un simple gasto imprevisto de caja chica en Dibal, el usuario debe abrir ventanas separadas, crear previamente una categoría, salir y volver a entrar; además, no se pueden cobrar cuentas desde la caja sin ir a la vista de mesas ni ver movimientos sin generar un arqueo completo.
  • Falta de Cohesión en Salón y Cocina: En Dibal las mesas son estáticas, no se pueden reacomodar ni acoplar lógicamente para grupos de más de 6 comensales; en cocina no existen semáforos temporizados de preparación, provocando que los pedidos salgan fríos o retrasados sin trazabilidad.
  • Riesgo Financiero y Descuadres: Se despachan comandas sin control estricto de caja abierta, y los ingresos/egresos no dejan rastro de origen ni destino, favoreciendo fugas de capital.

4. ANÁLISIS TÉCNICO EN PROFUNDIDAD DE LAS SOLUCIONES DE MAYOR PRIORIDAD

4.1. Prioridad 10: Arquitectura de Cola de Impresión en la Nube (Database Queue Proxy)

El talón de Aquiles de Dibal y de los sistemas web convencionales es la impresión física. Cuando una aplicación web se ejecuta bajo HTTPS en la nube (como https://bunker-proyect.vercel.app/), los navegadores modernos (Chrome, Safari, Edge) bloquean por seguridad cualquier intento de comunicación directa con una impresora local en HTTP o IP privada (error de Mixed Content y directivas CORS). Dibal soluciona esto de forma precaria obligando al cliente a usar un navegador modificado o en modo desarrollador con seguridad desactivada.

En Búnker ComandaGo diseñamos una arquitectura pionera denominada Database Queue Proxy:

┌─────────────────────────────────────────────────────────────────────────────────────────────┐ │ FLUJO DE LA COLA DE IMPRESIÓN PROXY EN LA NUBE │ └─────────────────────────────────────────────────────────────────────────────────────────────┘ [Dispositivo Mozo (iPad / Android)] ──HTTPS / TLS 1.3──► [Vercel Serverless Gateway] │ (INSERT INTO tickets_pendientes) ▼ [Supabase PostgreSQL Cloud] │ (Polling optimizado en segundo plano) ▼ [PC de Caja Local (Node.js Service)] (Ejecutado vía Iniciar_Impresora.vbs) │ (Envío de bytes RAW ESC/POS USB/Red) ▼ [Impresora Térmica 80mm] │ (UPDATE tickets_pendientes SET impreso=true) ▼ [Ticket Físico Emitido en Salón]

Ventajas de Ingeniería: El mozo puede comisionar comandas desde cualquier red celular (4G/5G) o Wi-Fi para clientes; el navegador no tiene contacto directo con la red interna del local. La PC de la caja actúa como despachador de cola, garantizando cero bloqueos de navegador y compatibilidad con cualquier dispositivo móvil moderno.

4.2. Prioridad 8: Script Invisible y Descubrimiento Autónomo de Impresoras (ARP Table)

En locales gastronómicos, los routers residenciales asignan direcciones IP mediante DHCP dinámico. Cuando se produce un corte de luz o se reinicia el router, la impresora térmica recibe una IP distinta (por ejemplo, pasa de 192.168.1.50 a 192.168.1.75), provocando que sistemas como Dibal colapsen y dejen de imprimir.

Búnker ComandaGo erradica XAMPP y Laragon implementando dos innovaciones:

  1. Arranque Silencioso en Windows: El script Iniciar_Impresora.vbs orquesta el proceso Node.js y el servicio de bandeja BunkerTray.ps1 en segundo plano sin desplegar ventanas negras de comandos ni requerir intervención del cajero.
  2. Mapeo Físico por MAC Address mediante Tabla ARP: El servidor local ejecuta periódicamente una consulta a la tabla ARP del sistema operativo (arp -a). Dado que la dirección MAC (identificador de hardware de la tarjeta de red de la impresora) nunca cambia, el sistema detecta automáticamente la nueva dirección IP asignada por el router y actualiza la ruta de socket TCP al instante sin interrumpir el servicio.
// Fragmento conceptual del resolvedor dinámico de impresoras por ARP
const { exec } = require('child_process');

function resolverIpPorMac(macDestino, callback) {
    exec('arp -a', (err, stdout) => {
        if (err) return callback(null);
        // Expresión regular para ubicar la IP asociada a la MAC registrada de la impresora
        const lineas = stdout.split('\n');
        for (let linea of lineas) {
            if (linea.toLowerCase().includes(macDestino.toLowerCase())) {
                const partes = linea.trim().split(/\s+/);
                return callback(partes[0]); // Retorna la nueva IP asignada por DHCP
            }
        }
        callback(null);
    });
}

4.3. Prioridad 9: Centralización Transaccional de Caja y Flujo Unificado

Frente a la dispersión de Dibal, Búnker concentra en el módulo de Caja el 100% de la operativa financiera:

  • Cobro Directo de Cuentas Pendientes: El cajero cuenta con un componente que lista en tiempo real todas las mesas con comanda activa. Con un clic abre el PaymentModal, calcula el vuelto exacto, aplica descuentos y liquida la cuenta sin forzar al usuario a desplazarse al plano del salón.
  • Modal Unificado de Movimientos: Registro ágil de entradas y salidas de efectivo con origen y destino forzoso (evitando el "dinero fantasma"), integrando el cálculo de saldo proyectado en tiempo real.
  • Arqueo Rápido y Cierre Ciego: El cajero declara el efectivo real contado sin ver el sistema; el algoritmo contrasta automáticamente: $\text{Efectivo Teórico} = \text{Monto Inicial} + \sum \text{Ingresos} - \sum \text{Egresos}$. El descuadre se calcula y archiva de forma inalterable.

5.2. Modelo Relacional y Unión Jerárquica de Mesas (Padre-Hijo)

Para dar respuesta a la Prioridad 7 (agrupación de mesas para grupos grandes), estructuramos en el modelo de datos de Prisma una autorreferencia jerárquica limpia: 

model Mesa {
  id          Int       @id @default(autoincrement())
  numero      String    @unique
  capacidad   Int
  estado      String    @default("libre") // libre, ocupada, cerrada
  posX        Float     @default(0)       // Coordenada X para Drag & Drop
  posY        Float     @default(0)       // Coordenada Y para Drag & Drop
  forma       String    @default("cuadrada")
  comandas    Comanda[]

  // Relación Padre-Hijo para unión y separación lógica de mesas
  mesaPadreId Int?
  mesaPadre   Mesa?     @relation("MesaUnion", fields: [mesaPadreId], references: [id])
  mesasHijas  Mesa[]    @relation("MesaUnion")

  @@index([estado])
}

Cuando se unen mesas, las mesas secundarias adoptan el mesaPadreId de la mesa principal. Toda orden se factura al ticket del nodo padre, pero visualmente el salón mantiene la ocupación de los espacios físicos reales.
